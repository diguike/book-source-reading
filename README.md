# 源码精读

> 一本持续追加的书。每一章是一个开源仓库的深度精读,目标是让读者读完能"自己也能造"。

## 这本书在做一件什么事

工程师吸收知识最高效的两种方式是:**亲手造一遍**,**或者读懂别人造好的**。前者门槛高、周期长;后者门槛低,但绝大多数源码精读文章止步于"它做了什么",不回答"它为什么这么做"和"换我来做会不会更好"。

这本书想把后者做到位。每一章挑一个**值得读、足够成熟、设计上有取舍可讲**的开源仓库,带着读者走完三件事:

1. **架构层** — 用一张图把这个项目的核心抽象讲清楚,对照源码目录树
2. **设计层** — 挑 3-5 个最有意思的取舍,讲清楚作者为什么选 A 没选 B
3. **品味层** — 诚实评价它的局限,你如果要重做会怎么改

不做"教程式 walk-through",不做"逐文件翻译",不当作者的形象代言人。

## 这本书写给谁

- 有 2 年以上工程经验的开发者,想从"能用"进阶到"能造"
- 对 AI Agent / LLM Infra / 开发者工具这些领域的开源项目有兴趣
- 习惯先读源码再相信文档,认同"看 README 不如看 internal/"
- **不适合**:刚学编程的新手(每章默认你能读懂目标项目的语言)、只想找现成方案抄的人(本书不提供"复制粘贴可用"的最小实现)

## 收录标准

不是所有热门项目都值得精读。新精读进入这本书必须同时满足:

1. **GitHub star ≥ 5K 或在领域内有明确影响力**(避免读完没人关心)
2. **核心模块在 10K 行代码以内**(读得动,讲得清,3-5 万字能讲透)
3. **设计上有真正的取舍**(纯 CRUD / 纯封装 / 纯算法实现的项目不收)
4. **代码质量在线**(屎山项目不收,读完只会让读者沮丧)

读者可以在 issue 里提名候选项目,但作者保留"哪些值得写"的最终判断。

## 一篇精读的标准结构

每篇精读固定 8 节,字数控制在 1.2-1.8 万字:

1. **场景钩子** — 一个具体需求开篇,讲为什么这个项目跑了出来
2. **全景架构** — 一张 Mermaid 图 + 目录树对照 + 核心抽象列表
3. **核心模块拆解** — 挑 2-4 个最值得讲的模块,每个配源码引用
4. **关键设计取舍** — 作者为什么选 A 没选 B,给出依据
5. **工程细节闲谈** — 选型、命名、目录组织上的小品味
6. **诚实评价 + 局限** — 写满,这是质量信号
7. **如果是你来做会怎么改** — 强迫自己有判断,不当应声虫
8. **延伸阅读** — 同领域相关项目、相关书

所有源码引用必须带 `path/to/file.ext:行号` 并锁定到具体 tag,不引 main 分支(防链接腐烂)。
